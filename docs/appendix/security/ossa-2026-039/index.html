OSSA-2026-039: HAProxy configuration injection leading to remote code execution in Octavia

PropertyValue
Date2026-09-21
CVECVE pending (requested from MITRE)
SeverityHigh
Affected ProjectOctavia
ReporterChen YuXiang (Institute of Computing Technology, Chinese Academy of Sciences), "Rolix" (Independent)

Summary​

Chen YuXiang of the Institute of Computing Technology, Chinese Academy of Sciences reported input validation flaws in the Octavia load balancer API. The tls_ciphers field of listeners and pools and the redirect_url and redirect_prefix fields of L7 policies were written into the HAProxy configuration that Octavia generates for the amphora without rejecting control characters. An authenticated user who owns a load balancer served by the Amphora provider can embed newlines in these fields and thereby inject arbitrary HAProxy configuration directives.

An independent reporter, "Rolix", subsequently demonstrated that the injection can be escalated to the execution of arbitrary commands as root on the provider-managed amphora. According to the upstream advisory this allows an attacker to disclose other tenants' TLS private keys and certificates and the deployment heartbeat key stored on the amphora, and to reach the control-plane network the amphora is attached to. The issue was reported to the OpenStack Vulnerability Management Team by Thomas Goirand of Infomaniak on behalf of the reporter.

Only the Amphora provider driver is affected. Other provider drivers, such as the OVN provider, do not render tenant input into an HAProxy configuration.

Upstream has not published a CVSS score for this issue. The severity rating above is OSISM's assessment: every project member who may create load balancers can gain root access to a virtual machine operated by the cloud provider and, from there, network access to the Octavia management network; exploitation requires valid credentials and a load balancer owned by the attacker.

Every OSISM deployment that runs an unpatched Octavia version with the Amphora provider is affected. Octavia and the Amphora provider are enabled in the OSISM defaults.

Affected Versions​

All OSISM releases up to and including 10.2.0 are affected, for every OpenStack release they support: the Kolla images pinned by OSISM 10.2.0 were built on 2026-08-14, before the upstream fixes merged. The OSISM or Octavia version alone does not tell whether a deployment already runs patched images, for example via rolling tags; use Check Whether the Patched Image Is Deployed for that.

The upstream advisory states the affected ranges as >=0.8.0 <16.1.0, ==17.0.0 and ==18.0.0. The fix is contained in Octavia 16.1.0 (2025.1/Epoxy), released on 2026-08-26. For 2025.2 (Flamingo) and 2026.1 (Gazpacho) only the versions 17.0.0 and 18.0.0 are released and both are vulnerable; the fixes are merged on the stable branches and the releases 17.0.1 and 18.0.1 are proposed but not published yet.

The tls_ciphers fields were introduced in Octavia 6.0.0. Older releases within the affected range are vulnerable only through the L7 policy redirect_url and redirect_prefix fields.

For Epoxy (2025.1), Flamingo (2025.2) and Gazpacho (2026.1) the container images build Octavia from the upstream stable branches, on which both fixes merged between 2026-08-24 and 2026-08-26. Rebuilt images include the fix without additional downstream patches; this applies to the rolling images built since then.

Patched container images are available for all OpenStack releases OSISM builds images for.

Impact on OSISM​

Octavia is enabled in the OSISM defaults (enable_octavia: "yes"), and kolla-ansible always enables the Amphora provider (octavia_provider_drivers). With the OSISM default neutron_plugin_agent: "ovn" the OVN provider is enabled in addition, but amphora stays the provider that is used when a user does not request one explicitly. A default OSISM deployment is therefore affected.

Exploitation requires an authenticated user who is allowed to create or update listeners, pools or L7 policies of a load balancer in their own project — the normal permission of every load balancer user. No administrative role is needed. The attacker does not need access to the Octavia management network; the injected configuration is delivered to the amphora by Octavia itself.

The vulnerable code — the API validation and the rendering of the HAProxy configuration — runs in the Octavia control plane services, not in the amphora image. That a compromised amphora has to be replaced after the control plane was patched (see Remediation) is OSISM's own assessment of the affected code path.

How to Check if You Are Affected​

warning

The docker commands in this section must be run on the nodes that run the Octavia containers, not on the manager node, where they return no result or a wrong result. The openstack commands are run on the manager node.

The Octavia services are not necessarily all on the same nodes. Their placement is defined by the inventory groups octavia-api, octavia-worker and octavia-health-manager. By default these are children of octavia, which in turn defaults to control. In production deployments with dedicated network nodes, octavia_worker and octavia_health_manager commonly run on the network nodes, while octavia_api runs on the control nodes. Check the inventory of the deployment for the members of these groups and run the commands on every node listed there.

Check Whether Octavia Is Deployed​

On every node in the octavia-api, octavia-worker and octavia-health-manager groups:

docker ps --format '{{.Names}}' | grep ^octavia

No output on all of these nodes means Octavia is not deployed and the deployment is not affected.

Check the Enabled Provider Drivers​

On a node in the octavia-api group (by default a control node):

docker exec octavia_api grep enabled_provider_drivers /etc/octavia/octavia.conf

If amphora is listed as an enabled provider driver, users can create vulnerable load balancers.

On the manager node, list the existing load balancers served by amphorae:

openstack --os-cloud admin loadbalancer list --provider amphora

These are the load balancers whose amphorae may already have received an injected configuration. The list tells whether the deployment is exposed to existing tenant input at all, and it is the set of load balancers to audit and, if necessary, fail over after the update, as described in Remediation and Mitigation. Deployments without any load balancer on the Amphora provider are affected but have nothing to audit.

Check the Running Octavia Version​

On a node in the octavia-api group (by default a control node):

docker exec octavia_api pip show octavia | grep ^Version

Versions below 16.1.0 as well as 17.0.0 and 18.0.0 are affected. Images built from a stable branch report a development version (for example 17.0.1.devN), which does not tell whether the fix is included — use the next check.

Check Whether the Patched Image Is Deployed​

The fix introduces VALID_CIPHER_RE and INVALID_URL_CHARS_RE in octavia/common/validate.py, which only exist in patched images. Run this on every node in the octavia-api, octavia-worker and octavia-health-manager groups. The loop only checks the Octavia containers that actually run on the node, so a node that hosts only some of the services (for example a network node with the worker and health manager) does not produce false results for the others:

for container in $(docker ps --format '{{.Names}}' | grep -E '^octavia_(api|worker|health_manager)$'); do
  docker exec $container /var/lib/kolla/venv/bin/python3 -c \
    "from octavia.common import validate as v; v.VALID_CIPHER_RE; v.INVALID_URL_CHARS_RE" \
    2>/dev/null && echo "$container: patched" || echo "$container: vulnerable"
done

vulnerable means the running image does not contain both fixes. No output means none of the three containers runs on this node. Collect the results from all nodes: the deployment is only fixed when every octavia_api, octavia_worker and octavia_health_manager container reports patched.

Vulnerability Details​

The Amphora provider renders the HAProxy configuration of a load balancer from a Jinja template in the Octavia control plane (JinjaTemplater in octavia/common/jinja/haproxy/combined_listeners/jinja_cfg.py) and uploads the result to the amphora. HAProxy configuration files are line-oriented: a value that contains a newline ends the directive it belongs to, and everything after it is parsed as additional directives or sections. Two groups of tenant-controlled fields reached the template without a check for such characters.

Bug #2162101 — Injection via the tls_ciphers field​

check_cipher_prohibit_list() in octavia/common/validate.py only split the cipher string of a listener or pool at : and compared the parts with the configured prohibit list; it did not restrict the characters of the string. _transform_listener() and _transform_pool() passed tls_ciphers unchanged to the template, where it ends up in the bind line of the frontend or the server lines of the backend.

The fix adds check_cipher_string(), which the API now calls for every cipher string and which only accepts the characters used by OpenSSL cipher strings:

VALID_CIPHER_RE = re.compile(r'^[A-Za-z0-9\-+!:@=_.]+\Z')

In addition, _transform_listener() and _transform_pool() verify the value again when the configuration is generated. A value in the database that does not match is replaced with [api_settings] default_listener_ciphers or [api_settings] default_pool_ciphers, and a warning is logged.

Bug #2162103 — Injection via L7 policy redirect URLs​

url() in octavia/common/validate.py validates redirect_url and redirect_prefix with the rfc3986 library. The library percent-encodes control characters before it validates the URL (a newline becomes %0A), so such URLs passed the structural checks. Octavia, however, stores the raw input, and _transform_l7policy() wrote it unencoded into the redirect location and redirect prefix lines of the HAProxy configuration.

The fix rejects URLs that contain control characters or spaces before they are passed to rfc3986:

INVALID_URL_CHARS_RE = re.compile(r'[\x00-\x20\x7f-\x9f]')

The new _sanitize_url() in jinja_cfg.py applies the same expression when the configuration is generated and clears a redirect_url or redirect_prefix from the database that does not pass, logging a warning.

Bug #2167565 — Escalation to remote code execution​

Both issues were originally triaged upstream as a low-severity hardening opportunity, and the fixes were developed and merged in public. They were reclassified after a proof of concept showed that injected HAProxy directives can be used to execute arbitrary commands as root on the amphora. With root access to the amphora an attacker can read the TLS certificates and private keys and the heartbeat key stored there, and can use the amphora's interface in the Octavia management network to reach the control plane. This bug has no fix of its own: it is closed by the two changes above.

Prerequisite Changes​

The upstream fix consists of two changes per branch that OSISM ships together in the patched images. The second change uses the imports and the logger that the first one adds to jinja_cfg.py, so they have to be applied in this order:

  1. Fix HAProxy config injection via tls_ciphers field (Bug #2162101) — validates the cipher strings of listeners and pools in the API and when the configuration is generated.
  2. Fix HAProxy config injection via L7 policy redirect URLs (Bug #2162103) — rejects control characters and spaces in redirect_url and redirect_prefix in the API and when the configuration is generated.
warning

Behavior changes after the fix:

  • The API rejects tls_ciphers values that contain characters other than alphanumerics, -, +, !, :, @, =, _ and ., and redirect URLs that contain spaces or control characters, with a validation error.
  • Invalid values that are already stored in the database are not removed. They are replaced with the default ciphers (tls_ciphers) or dropped (redirect_url, redirect_prefix) the next time the configuration of the load balancer is generated, which changes the behavior of the affected listener, pool or L7 policy.

Remediation​

For OSISM Releases​

Because 2024.1 (Caracal) and 2024.2 (Dalmatian) receive no fixed upstream release, OSISM provides the fix for these releases as downstream patches for the Octavia container images via the following change:

  • container-images-kolla commit efaa873 (PR #803) — community-curated backport for 2024.1 (Caracal) and 2024.2 (Dalmatian); it also re-enables the build of the Octavia images for 2024.1

For 2025.1 (Epoxy), 2025.2 (Flamingo) and 2026.1 (Gazpacho) the container images build Octavia from the upstream stable branches, which contain the fix as of Octavia 16.1.0 and the upcoming 17.0.1 and 18.0.1. Rebuilt images include the fix automatically.

Patched rolling images are available for 2024.1, 2024.2, 2025.1, 2025.2, and 2026.1.

No OSISM release up to and including 10.2.0 ships the patched Octavia container images; on these releases the fix can only be obtained through the rolling tags as described below. A fix will be included in the next OSISM release. Consult the OSISM Release Notes for version information and availability.

The affected code runs in the Octavia API service (input validation) and in the services that generate the HAProxy configuration (octavia_worker, and octavia_health_manager during failovers). Using rolling tags, override all Octavia container images in environments/kolla/images.yml. With a stable OSISM release the Kolla images are pulled from the kolla/release/<openstack_version> namespace with pinned version tags (docker_namespace in environments/kolla/configuration.yml), whereas the rolling images live in the kolla namespace. The image parameters therefore have to be overridden together with the tag; the tag override alone would point at an image that does not exist:

environments/kolla/images.yml
octavia_tag: "2024.1"  # or "2024.2", "2025.1", "2025.2", "2026.1", depending on your OpenStack release
octavia_api_image: "registry.osism.tech/kolla/octavia-api"
octavia_driver_agent_image: "registry.osism.tech/kolla/octavia-driver-agent"
octavia_health_manager_image: "registry.osism.tech/kolla/octavia-health-manager"
octavia_housekeeping_image: "registry.osism.tech/kolla/octavia-housekeeping"
octavia_worker_image: "registry.osism.tech/kolla/octavia-worker"

Replace registry.osism.tech if you pull the images from a mirror. Verify the deployed images on every Octavia node with the check in Check Whether the Patched Image Is Deployed.

The amphora image does not contain the affected code and does not need to be rebuilt for this issue. The OSISM defaults set octavia_amp_image_tag: amphora independently of octavia_tag, so the override above does not change which amphora image is used.

Updating the control plane does not repair amphorae that already run an injected configuration. After the update, audit the existing load balancers as described below and fail over every load balancer with a suspicious value, which replaces its amphorae with new instances:

openstack --os-cloud admin loadbalancer failover <loadbalancer>

Mitigation​

The affected fields cannot be disabled by configuration, and the Octavia policies cannot restrict individual fields of a listener, pool or L7 policy. Applying the patched container images is the only effective remediation. Until the fix is deployed, and afterwards to detect earlier exploitation, consider the following measures:

  1. Auditing the existing listeners and pools for cipher strings with unexpected characters. Every line of output names a resource and its project that must be investigated:

    for type in listener pool; do
      for id in $(openstack --os-cloud admin loadbalancer $type list -f value -c id); do
        openstack --os-cloud admin loadbalancer $type show "$id" -f json | python3 -c '
    import json, re, sys
    d = json.load(sys.stdin)
    if re.search(r"[^A-Za-z0-9\-+!:@=_.]", d.get("tls_ciphers") or ""):
        print(sys.argv[1], d["id"], d["project_id"])' $type
      done
    done

  2. Auditing the existing L7 policies for redirect URLs with spaces or control characters:

    for id in $(openstack --os-cloud admin loadbalancer l7policy list -f value -c id); do
      openstack --os-cloud admin loadbalancer l7policy show "$id" -f json | python3 -c '
    import json, re, sys
    d = json.load(sys.stdin)
    for field in ("redirect_url", "redirect_prefix"):
        if re.search(r"[\x00-\x20\x7f-\x9f]", d.get(field) or ""):
            print("l7policy", d["id"], d["project_id"], field)'
    done

  3. Treating every hit as a potential compromise of the amphorae of that load balancer: fail over the load balancer once the patched images are deployed, replace the TLS certificates and private keys that were configured on it, and review the activity of the owning project.

  4. Monitoring the logs of octavia_worker and octavia_health_manager after the update for the messages has invalid tls_ciphers in DB, falling back to default and in DB, clearing. They are written when a stored value is neutralized and identify the affected listener, pool or L7 policy.

  5. Verifying that the security groups and firewall rules of the Octavia management network only allow the traffic Octavia needs between the amphorae and the control plane (the amphora agent port 9443/tcp towards the amphorae, the health manager port 5555/udp towards the control plane). This limits what an attacker can reach from a compromised amphora.
