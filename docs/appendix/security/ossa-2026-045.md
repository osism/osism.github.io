# OSSA-2026-045: Cross-project information disclosure in Cinder Messages API

| Property         | Value                                                                                                     |
|:-----------------|:----------------------------------------------------------------------------------------------------------|
| Date             | 2026-10-20                                                                                                |
| CVE              | [CVE-2026-93856](https://www.cve.org/CVERecord?id=CVE-2026-93856)                                         |
| Severity         | Medium                                                                                                    |
| Affected Project | Cinder                                                                                                    |
| Reporter         | Yuliang Xiao (Independent), Chen YuXiang (Institute of Computing Technology, Chinese Academy of Sciences) |

## Summary

Yuliang Xiao, an independent reporter, and Chen YuXiang of the Institute of Computing Technology,
Chinese Academy of Sciences independently reported that the "List messages" call of the Cinder Block
Storage API (`GET /v3/{project_id}/messages`, available since API microversion 3.3) is not
restricted to the project of the caller. A user with the `member` or `reader` role in any project
receives the non-expired user messages of all projects.

Cinder records a user message when an asynchronous operation on a volume, snapshot or backup fails,
for example when the scheduler finds no backend for a new volume or an image cannot be copied to a
volume. The response therefore discloses the UUIDs and types of resources owned by other projects,
together with the request IDs, the timestamps and the text of these messages. The message texts are
generic by design, and the response does not contain the project IDs of the other projects.

Upstream has not published a CVSS score for this issue. The severity rating above is OSISM's
assessment (CVSS 3.1 base score 4.3, `AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:N`): every project member
or reader can exploit the issue with a single API call, but the disclosed information is limited to
resource identifiers and generic status messages and does not grant access to the resources of
other projects.

**Every OSISM deployment running an unpatched Cinder version is affected.** Cinder is enabled in the
OSISM defaults.

## Affected Versions

**All OSISM releases up to and including 10.3.0 and 11.0.1 are affected.** The Kolla images pinned
by OSISM 10.3.0 (OpenStack 2025.1) and 11.0.1 (OpenStack 2026.1) were built on 2026-10-01 and
2026-10-11, before the fix was available. The OSISM or Cinder version alone does not tell whether a
deployment already runs a patched image, for example via rolling tags; use
[Check Whether the Patched Image Is Deployed](#check-whether-the-patched-image-is-deployed) for
that.

The upstream advisory states the affected ranges as `>=9.0.0 <26.3.1`, `==27.0.0`, `==28.0.0` and
`==29.0.0`, so the fix for 2025.1 (Epoxy) is expected in Cinder 26.3.1. For 2025.2 (Flamingo),
2026.1 (Gazpacho) and 2026.2 (Hibiscus) only the versions 27.0.0, 28.0.0 and 29.0.0 are released,
and all three are vulnerable; the fixes are expected in the next point release of each series. The
user messages API first appeared in Cinder 9.0.0 (Newton), so every series since then is affected,
including 2024.1 (Caracal) and 2024.2 (Dalmatian).

**At the time of this advisory there is no fixed Cinder release available upstream for any
series.** The upstream fixes are still under review on OpenDev and have not merged yet.

Caracal (2024.1) is unmaintained and Dalmatian (2024.2) reached end of life on 2026-04-29 upstream;
neither will receive an official fixed release, and no upstream backport has been proposed for these
branches. For these two releases OSISM provides the fix as a community-curated backport of the
2025.1 patch, shipped as a downstream patch in the Cinder container images.

For Epoxy (2025.1), Flamingo (2025.2) and Gazpacho (2026.1) the OSISM container images carry the
proposed upstream patch ahead of its official upstream release.

Patched container images are available for all OpenStack releases OSISM builds images for.

## Impact on OSISM

Cinder is enabled in the OSISM defaults (`enable_cinder: "yes"`); only deployments that set
`enable_cinder: "no"` in `environments/kolla/configuration.yml` do not run it. The user messages API
is always part of the Cinder API; there is no option to disable it. The list call is governed by the
policy `message:get_all`, which by default admits every user with the `reader` or `member` role in a
project, and OSISM does not override this policy. A default OSISM deployment is therefore affected.

Exploitation requires nothing but a token for a project in which the attacker holds one of these
roles; neither an administrative role nor a particular configuration is needed. The response
contains every message that has not been removed yet. Messages expire after `[DEFAULT] message_ttl`
(default 30 days) and are deleted by a periodic task of `cinder-scheduler` every
`[DEFAULT] message_reap_interval` (default 24 hours); neither OSISM nor kolla-ansible changes these
options. How much is exposed therefore depends on how many operations of other projects failed
during that period. The disclosed resource UUIDs do not grant access to the resources themselves,
and because the response contains no project IDs, attributing a resource to a project requires a
separate source of information.

The vulnerable code path runs only in the Cinder API service (`cinder_api` container). The
`cinder-scheduler`, `cinder-volume` and `cinder-backup` services create user messages but never list
them. That only the `cinder-api` image has to be updated is OSISM's own assessment of the affected
code path.

### How to Check if You Are Affected

Run the `docker` commands on every node of the `cinder-api` inventory group (by default the control
nodes) and the `openstack` command on the manager node.

#### Check Whether Cinder Is Deployed

```bash
docker ps --format '{{.Names}}' | grep ^cinder_api
```

No output on all nodes of the `cinder-api` group means the Cinder API is not deployed and the
deployment is **not affected**.

#### Check the Running Cinder Version

```bash
docker exec cinder_api pip show cinder | grep ^Version
```

Because no fixed Cinder release exists upstream yet, your deployment is **affected** unless you have
deployed an OSISM container image that includes the patch (see Remediation). Images built from a
stable branch report a development version such as `26.3.1.dev1`, and the release tags of the
images pinned by OSISM 10.3.0 carry `26.3.1` in their name (`26.3.1.20261001`). Neither means that
the fix is included; use the next check.

#### Check Whether the Patched Image Is Deployed

The fix changes the default of the `project_only` parameter of `_messages_get_query()` from `False`
to `True`:

```bash
docker exec cinder_api /var/lib/kolla/venv/bin/python3 -c \
  "import inspect; from cinder.db.sqlalchemy import api; \
print(inspect.signature(api._messages_get_query).parameters['project_only'].default)"
```

`True` means the running image contains the fix, `False` means it is **vulnerable**. The deployment
is only fixed when the check prints `True` on every node of the `cinder-api` group.

#### Check Which User Messages Are Exposed

```bash
openstack --os-cloud admin --os-volume-api-version 3.3 volume message list
```

An administrator sees the messages of all projects. On an unpatched deployment every user with the
`member` or `reader` role in any project sees the same list. An empty list means that nothing is
exposed at the moment; new messages are created whenever an asynchronous operation fails.

## Vulnerability Details

The user messages API is implemented by `MessagesController` in `cinder/api/v3/messages.py`. The
"Show message" and "Delete message" calls load a single message through `message_get()`, which
queries the database in `_message_get()` with `project_only="yes"`, so a regular user only finds
the messages of their own project. These two calls are not affected.

`MessagesController.index()`, which implements the "List messages" call, authorizes the policy
`message:get_all` without a target object. `context.authorize()` then checks the policy against the
caller's own project, which every user with the `reader` or `member` role in that project passes.
The request parameters are handed on through `API.get_all()` in `cinder/message/api.py` to
`message_get_all()` in `cinder/db/sqlalchemy/api.py`, which builds its query with
`_generate_paginate_query()` and the query helper registered for messages in `PAGINATION_HELPERS`,
`_messages_get_query()`:

```python
def _messages_get_query(context, project_only=False):
    return model_query(context, models.Message, project_only=project_only)
```

`model_query()` only restricts a query to the caller's project when `project_only` is set and the
request comes from a regular user (`is_user_context()`). Because `_generate_paginate_query()` calls
the helper without further arguments, the default `project_only=False` applied, no project filter
was added, and the list contained the messages of all projects.

The fix changes the default to `project_only=True`:

```python
def _messages_get_query(context, project_only=True):
    return model_query(context, models.Message, project_only=project_only)
```

Regular users now only receive the messages of their own project. Administrators keep seeing the
messages of all projects, because `model_query()` does not apply the project filter to admin
contexts. On 2026.1 and older releases the function is located in `cinder/db/sqlalchemy/api.py`, on
2026.2 and master in `cinder/db/api.py`. The fix also adds unit tests which verify that
`message_get_all()` and `message_get()` only return messages of the caller's project. It introduces
no configuration options and no API changes; the only visible change is that regular users no
longer see the messages of other projects.

## Remediation

### For OSISM Releases

Because no fixed Cinder release is available upstream, OSISM provides the fix as downstream patches
for the Cinder container images via the following change:

- [container-images-kolla commit b56b799](https://github.com/osism/container-images-kolla/commit/b56b7999e3bd104ade55119b2811de463d60edc1)
  ([PR #820](https://github.com/osism/container-images-kolla/pull/820)) — the proposed upstream
  patches for 2025.1 (Epoxy), 2025.2 (Flamingo) and 2026.1 (Gazpacho), and a community-curated
  backport of the 2025.1 patch for 2024.1 (Caracal) and 2024.2 (Dalmatian); it also re-enables the
  build of the Cinder images for 2024.1

Patched rolling images are available for 2024.1, 2024.2, 2025.1, 2025.2, and 2026.1.

No OSISM release up to and including 10.3.0 and 11.0.1 ships the patched Cinder container images;
on these releases the fix can only be obtained through the rolling tags as described below. A fix
will be included in upcoming OSISM releases that ship the patched Cinder container images. Consult
the [OSISM Release Notes](../../release-notes/) for version information and availability.

The vulnerable code path runs in the Cinder API service (`cinder_api` container), so it is
sufficient to update the `cinder-api` container image. Using rolling tags, override it in
`environments/kolla/images.yml`. With a stable OSISM release the Kolla images are pulled from the
`kolla/release/<openstack_version>` namespace with pinned version tags (`docker_namespace` in
`environments/kolla/configuration.yml`), whereas the rolling images live in the `kolla` namespace.
The image parameter therefore has to be overridden together with the tag; the tag override alone
would point at an image that does not exist:

```yaml title="environments/kolla/images.yml"
cinder_api_tag: "2024.1"  # or "2024.2", "2025.1", "2025.2", "2026.1", depending on your OpenStack release
cinder_api_image: "registry.osism.tech/kolla/cinder-api"
```

Replace `registry.osism.tech` if you pull the images from a mirror. Verify the deployed image on
every node of the `cinder-api` group with the check in
[Check Whether the Patched Image Is Deployed](#check-whether-the-patched-image-is-deployed).

The `cinder-scheduler`, `cinder-volume` and `cinder-backup` images contain the same code but never
run the message list query; they do not need to be updated for this issue.

### Mitigation

Every OSISM deployment that runs Cinder is affected, and the vulnerable call is available to every
project member and reader. Applying the patched container image is the only complete remediation.
Until it is deployed, consider the following measures:

1. Restricting the list call to administrators through a policy override. Add the following to
   `environments/kolla/files/overlays/cinder/policy.yaml` in the configuration repository (create
   the file if it does not exist) and apply it with `osism apply -a reconfigure cinder`:

   ```yaml title="environments/kolla/files/overlays/cinder/policy.yaml"
   "message:get_all": "rule:context_is_admin"
   ```

   This closes the vulnerable code path completely. It also removes the message list for regular
   users: `openstack volume message list` fails for them, and the Messages tabs of volumes,
   snapshots and backups in Horizon can no longer retrieve messages. Showing or deleting a message
   by its ID keeps working. Remove the override once the patched image is deployed.

2. Monitoring the Cinder API logs for list calls. The Cinder API logs every request together with
   the user and project ID of the caller:

   ```bash
   docker exec cinder_api grep -E 'GET [^ ]+/messages([?][^ ]*)?$' /var/log/kolla/cinder/cinder-api.log
   ```

   Before the fix, a list call of a regular user without a `resource_uuid` filter returned the
   messages of all projects. Calls with a `resource_uuid` filter, as Horizon sends them for the
   Messages tab of a volume, snapshot or backup, only return the messages of that resource. With
   central logging, which is enabled in the OSISM defaults, search for these requests in OpenSearch
   to cover the whole retention period.
