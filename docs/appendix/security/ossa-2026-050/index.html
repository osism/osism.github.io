OSSA-2026-050: keystonemiddleware access rules bypass via X-Service-Token

PropertyValue
Date2026-10-29
CVECVE-2026-115642
SeverityHigh
Affected Projectkeystonemiddleware
ReporterNassim Abbaoui (OVHcloud)

Summary​

Nassim Abbaoui of OVHcloud reported that the auth_token middleware of keystonemiddleware skips the enforcement of application credential access rules as soon as a request carries an X-Service-Token header, regardless of whether that service token is valid. Access rules restrict an application credential to individual API calls (service, method and path). Anyone holding an access-restricted application credential can bypass these restrictions by adding an X-Service-Token header to the request; depending on the service, the header has to contain a valid token, such as a token of the same credential, or any value at all. The credential then acts with the full role-based permissions of the user who created it in every OpenStack API that uses the auth_token middleware.

The same check also skipped token binding ([keystone_authtoken] enforce_token_bind, for example Kerberos) when delay_auth_decision is enabled. OSISM does not use token binding.

The CVE record rates the issue with a CVSS 3.1 base score of 8.3 (AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:L).

Only deployments in which application credentials with access rules are in use are affected.

Affected Versions​

The upstream advisory states the affected ranges as <10.9.2, >=10.10.0 <10.12.2, >=11.0.0 <12.0.1 and >=13.0.0 <13.0.2. The fixed upstream releases are keystonemiddleware 10.9.2 for 2025.1 (Epoxy), 10.13.0 for 2025.2 (Flamingo), 12.1.0 for 2026.1 (Gazpacho) and 13.0.2 for 2026.2 (Hibiscus). The versions 10.12.2 and 12.0.1, which the ranges imply, have not been released.

All OSISM releases up to and including 10.3.0 and 11.0.2 are affected. The Kolla images pinned by these releases contain keystonemiddleware 10.12.1 (OpenStack 2025.1) and 12.0.0 (OpenStack 2026.1). Use Check the Running keystonemiddleware Version to find out whether a deployment already runs a fixed version, for example via rolling tags.

The Kolla images install keystonemiddleware from PyPI at the version pinned in the upper constraints of the OpenStack requirements project. For 2025.1 (Epoxy), 2025.2 (Flamingo) and 2026.1 (Gazpacho) upstream has raised these constraints to the fixed releases; rebuilt images include the fix without additional downstream patches.

Caracal (2024.1) is unmaintained and Dalmatian (2024.2) reached end of life on 2026-04-29 upstream; neither will receive an official fixed release. For these two releases OSISM pins a fixed keystonemiddleware release of a newer series in the upper constraints: 10.9.2 (2025.1 line) for 2024.1 and 10.13.0 (2025.2 line) for 2024.2. Both releases also contain the fix for OSSA-2026-001.

Patched container images are available for all OpenStack releases OSISM builds images for; the patched rolling images have been available since 2026-11-03.

Impact on OSISM​

keystonemiddleware is a library. Its auth_token middleware validates the tokens of incoming requests in the API services of every OpenStack project except Keystone itself. In a default OSISM deployment these are Nova, Neutron, Glance, Placement, Cinder, Designate and Octavia; further API services such as Barbican, Manila, Ironic, Magnum, Aodh or Gnocchi are affected as well when they are enabled.

Application credentials with access rules are not created by OSISM or kolla-ansible. They are created by users, who are allowed to do so under the default Keystone policies. A deployment is therefore affected as soon as a user restricts an application credential with access rules and hands it to a party that should only be able to make the permitted calls, for example a CI system or a monitoring agent. That party can then use the credential with the full permissions of its owner. Application credentials without access rules and regular user tokens are not affected.

kolla-ansible does not set service_token_roles_required for Nova, Neutron, Glance, Placement and Octavia, so these API services accept any valid token as a service token and are exploitable; the Glance API additionally runs with delay_auth_decision = true (see Vulnerability Details). Cinder and Designate set service_token_roles_required = true, which blocks the bypass for users without a service role. That Cinder and Designate are not exploitable in a default OSISM deployment is OSISM's own assessment of the affected code path; update their images nevertheless.

How to Check if You Are Affected​

Run the docker commands on every node that runs OpenStack API services (by default the control nodes).

Check Whether Application Credentials With Access Rules Exist​

On a node of the mariadb group, enter the MariaDB root password (database_password in environments/kolla/secrets.yml) when prompted:

docker exec -it mariadb mariadb -uroot -p -N -B -e \
  'SELECT COUNT(DISTINCT application_credential_id) FROM keystone.application_credential_access_rule;'

0 means that no application credential with access rules exists at the moment and the issue cannot be exploited. Users can create such credentials at any time, so update the images anyway.

Check the Running keystonemiddleware Version​

for c in $(docker ps --format '{{.Names}}' | grep -E '(_api|_api_cfn|^neutron_server|^swift_proxy_server)$'); do
  echo -n "$c: "; docker exec "$c" pip show keystonemiddleware | grep ^Version
done

Compare each version with the affected ranges above. 10.9.2, 10.13.0, 12.1.0 and 13.0.2 are fixed; 10.12.1 and 12.0.0, which the images of OSISM 10.3.0 and 11.0.2 contain, are vulnerable. The deployment is only fixed when every API container on every node reports a fixed version.

Vulnerability Details​

BaseAuthProtocol.validate_allowed_request() in keystonemiddleware/auth_token/__init__.py checks the request against the access rules of the application credential in the user token. A request that carries a service token is part of a chain of service-to-service calls (for example Nova calling Cinder on behalf of a user) and is therefore exempt from the access rules. The function tested only for the presence of the X-Service-Token header, not for the result of its validation:

if request.service_token:
    return

How the bypass is exploited depends on the configuration of the service:

  • With [keystone_authtoken] service_token_roles_required = False, the upstream default before the fix, the middleware accepts any valid token as a service token. The attacker sends a token issued for the restricted application credential in both X-Auth-Token and X-Service-Token; both tokens are valid, the access rules are skipped, and the request is accepted.
  • With delay_auth_decision enabled, as in the Glance API, an invalid service token does not lead to a rejection; the request continues as a regular user request. Any value in X-Service-Token is sufficient.
  • With service_token_roles_required = True and delay_auth_decision disabled, the middleware rejects the request with 401 because the service token is not valid, unless the attacker also holds a token with one of the roles in [keystone_authtoken] service_token_roles.

The same presence test decided whether _confirm_token_bind() runs, so a service token also skipped token binding.

The fix requires a validated service token in both places:

if request.service_token and request.service_token_valid:
    return

Because a valid token is still accepted as a service token while service_token_roles_required = False, the fixed releases also change the default of this option to True. Only then is a token without a service role rejected as service token, and the access rules are enforced.

Prerequisite Changes​

The upstream fix consists of two changes per stable series, which the fixed releases ship together:

  1. Change service_token_roles_required default config — sets [keystone_authtoken] service_token_roles_required to True, so that a token in X-Service-Token is only accepted as a service token when its user holds one of the roles in [keystone_authtoken] service_token_roles (default: service). On master and 2026.2 this default was already in place before the fix; keystonemiddleware 13.0.0 contains it.
  2. Fix service-token presence bypass of access_rules and token bind (Bug #2162748) — requires a valid service token before skipping the access rules or the token binding check.
warning

The new default service_token_roles_required = True makes OpenStack services reject service tokens whose user does not hold a role from service_token_roles. In kolla-ansible only Nova sends service tokens ([service_user] send_service_user_token = true), and its service user nova is granted the service role in the service project. Blazar, Cinder, Designate, Masakari and Watcher already set service_token_roles_required = true explicitly. Default OSISM deployments are therefore not expected to change behavior. Deployments that send service tokens as a user without the service role, for example through configuration overlays, receive 401 responses on these inter-service requests after the update. Do not set service_token_roles_required = false to work around this: it reopens the bypass.

Remediation​

For OSISM Releases​

The Kolla images install keystonemiddleware at the version pinned in the upper constraints. OSISM pinned the fixed releases for all OpenStack releases it builds images for with the following change:

  • container-images-kolla commit 147fb67 (PR #828) — pins keystonemiddleware 10.9.2 for 2024.1, 10.13.0 for 2024.2, 2025.1 and 2025.2, and 12.1.0 for 2026.1

After upstream raised the upper constraints of 2025.1, 2025.2 and 2026.1 to the fixed releases, the OSISM pins for these three releases were removed again:

  • container-images-kolla commit aea4cc3 (PR #831) — the images of 2025.1 now contain keystonemiddleware 10.9.2 from the upstream constraints instead of 10.13.0; 2025.2 and 2026.1 keep 10.13.0 and 12.1.0

Patched rolling images are available for 2024.1, 2024.2, 2025.1, 2025.2, and 2026.1.

No OSISM release up to and including 10.3.0 and 11.0.2 ships the patched container images; on these releases the fix can only be obtained through the rolling tags as described below. A fix will be included in upcoming OSISM releases that ship the patched container images. Consult the OSISM Release Notes for version information and availability.

The vulnerable code runs in the API service of every OpenStack project that uses the auth_token middleware, so the API images of all enabled services have to be updated. Using rolling tags, override them in environments/kolla/images.yml. With a stable OSISM release the Kolla images are pulled from the kolla/release/<openstack_version> namespace with pinned version tags (docker_namespace in environments/kolla/configuration.yml), whereas the rolling images live in the kolla namespace. The image parameters therefore have to be overridden together with the tags; the tag override alone would point at images that do not exist. The following covers the API services of a default OSISM deployment:

environments/kolla/images.yml
nova_api_tag: "2025.1"  # or "2024.1", "2024.2", "2025.2", "2026.1", depending on your OpenStack release
nova_api_image: "registry.osism.tech/kolla/nova-api"
neutron_server_tag: "2025.1"
neutron_server_image: "registry.osism.tech/kolla/neutron-server"
glance_api_tag: "2025.1"
glance_api_image: "registry.osism.tech/kolla/glance-api"
placement_api_tag: "2025.1"
placement_api_image: "registry.osism.tech/kolla/placement-api"
cinder_api_tag: "2025.1"
cinder_api_image: "registry.osism.tech/kolla/cinder-api"
designate_api_tag: "2025.1"
designate_api_image: "registry.osism.tech/kolla/designate-api"
octavia_api_tag: "2025.1"
octavia_api_image: "registry.osism.tech/kolla/octavia-api"

Add the *_api_tag and *_api_image parameters of every further API service you have enabled in the same way, for example barbican_api_tag and barbican_api_image with the image registry.osism.tech/kolla/barbican-api. Replace registry.osism.tech if you pull the images from a mirror.

Commit the override to the configuration repository and roll it out:

osism apply configuration
osism apply -a pull nova
osism apply nova
osism apply -a pull neutron
osism apply neutron
osism apply -a pull glance
osism apply glance
osism apply -a pull placement
osism apply placement
osism apply -a pull cinder
osism apply cinder
osism apply -a pull designate
osism apply designate
osism apply -a pull octavia
osism apply octavia

See Security Updates for the individual steps, how to verify the deployed image, and when to remove the override again.

The other images of these services (for example nova-conductor, neutron-metadata-agent or cinder-volume) contain keystonemiddleware as well but do not run the auth_token middleware; they do not need to be updated for this issue. Keystone does not use the auth_token middleware.

Mitigation​

Deployments without application credentials that carry access rules (see Check Whether Application Credentials With Access Rules Exist) cannot be exploited at the moment; updating the images at the next regular maintenance is sufficient. Otherwise, applying the patched container images is the only complete remediation. Until they are deployed, consider the following measures:

  1. Reviewing which application credentials carry access rules and who holds them. List the affected credentials and their owners on a node of the mariadb group:

    docker exec -it mariadb mariadb -uroot -p -e \
      'SELECT DISTINCT ac.id, ac.name, ac.user_id, ac.project_id
       FROM keystone.application_credential ac
       JOIN keystone.application_credential_access_rule acar
         ON acar.application_credential_id = ac.internal_id;'

    Ask the owners to delete credentials that have been handed to parties that are not trusted with the full permissions of the owner, and to issue them again once the patched images are deployed.

  2. Requiring a service role for service tokens ahead of the update. Add the option of the fixed releases to the configuration overlays of the services that do not set it, for example for Nova:

    environments/kolla/files/overlays/nova.conf
    [keystone_authtoken]
    service_token_roles_required = true

    Do the same in neutron.conf, placement.conf, octavia.conf and in the overlays of further enabled API services, and apply the change with osism apply -a reconfigure <service>. This closes the bypass in these services; the behavior change described in the warning above applies in the same way. It does not protect the Glance API, which accepts any value in X-Service-Token because of delay_auth_decision.

The bypass leaves no specific trace in the logs: the middleware logs a valid token that fails the role check as a service token only once per process, and the request itself looks like any other API call.
