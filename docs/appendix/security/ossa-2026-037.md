# OSSA-2026-037: Inconsistent scope enforcement for delegated tokens in Keystone

| Property         | Value                                                                                                                                |
|:-----------------|:-------------------------------------------------------------------------------------------------------------------------------------|
| Date             | 2026-08-25                                                                                                                           |
| CVE              | [CVE-2026-80182](https://www.cve.org/CVERecord?id=CVE-2026-80182), [CVE-2026-80184](https://www.cve.org/CVERecord?id=CVE-2026-80184) |
| Severity         | High                                                                                                                                 |
| Affected Project | Keystone                                                                                                                             |
| Reporter         | Grzegorz Grasza (Red Hat), Tim Shephard (roiai.ca)                                                                                   |

## Summary

Two related vulnerabilities were discovered in OpenStack Keystone concerning tokens obtained through
delegated credentials — application credentials, EC2 credentials, and OAuth1 access tokens.

Grzegorz Grasza of Red Hat reported that Keystone did not consistently block delegated tokens from
creating new long-lived credentials or authorizing new delegations (Bug #2153453). A token derived
from an EC2 credential or an OAuth1 access token could create, list, read, and delete trusts, and an
EC2-derived token could create application credentials and authorize OAuth1 request tokens. Each of
these operations mints a new, independent grant that persists after the original credential is
revoked. Because trust creation validates the requested roles against the trustor's full role
assignments rather than against the roles of the delegated token, a narrowly scoped OAuth1 or EC2
token could additionally delegate roles it was never authorized for.

Tim Shephard of roiai.ca separately reported that delegated tokens could be submitted to the token
authentication method of `POST /v3/auth/tokens` to escape their project scope (Bug #2158538). An
application credential token presented without an explicit scope was rescoped to the credential
owner's default project instead of the project the credential was issued for, and an EC2-derived
token could be rescoped to any project the underlying user holds a role in.

**Every OSISM deployment running an unpatched Keystone version is affected.** Application
credentials, EC2 credentials, trusts, and the token authentication method are available in every
Keystone deployment, `[token] allow_rescope_scoped_token` is enabled by default, and there is no
configuration that makes a deployment immune. Exploitation requires possession of a delegated
credential, for example a leaked application credential or EC2 key pair.

Upstream has not published a CVSS score for this issue, and the two CVE ids requested from MITRE are
still pending. The severity rating above is OSISM's assessment: an attacker holding a delegated
credential can turn it into persistent access that survives revocation of that credential, obtain
roles beyond the delegation, and reach other projects of the credential owner.

## Impact on OSISM

Keystone is a core service of every OSISM deployment, and all delegation mechanisms involved are
available by default:

- **Application credentials** can be created by every user for their own projects. They are the
  recommended way to give automation access to the cloud and are widely used.
- **EC2 credentials** are used to access the S3 API of Ceph RGW or Swift with Keystone identities.
  Every user can create them.
- **OAuth1** is part of Keystone's default `[auth] methods`
  (`external,password,token,oauth1,mapped,application_credential`), which OSISM does not change.
  Kolla only replaces the list when Keystone federation is enabled
  (`password,token,openid,application_credential`), which removes OAuth1 but leaves the other
  paths open.
- **Trusts** are created on behalf of users by services such as Heat and Magnum, and every user can
  create them.
- The token authentication method and `[token] allow_rescope_scoped_token = True` are Keystone
  defaults that OSISM does not change.

Exploitation requires an attacker to hold a delegated credential of a victim — a leaked application
credential, an EC2 access/secret key pair, or an OAuth1 access token — or a user to deliberately
abuse their own narrow delegation. In both cases the attacker gains more than the delegation was
meant to grant: persistent credentials that survive revocation of the original one, trusts carrying
roles the delegation never had, and tokens for other projects of the credential owner.

### How to Check if You Are Affected

#### Check the Running Keystone Version

```bash
docker exec keystone pip show keystone | grep ^Version
```

Because no fixed Keystone release exists upstream yet, your deployment is **affected** unless you
have deployed an OSISM container image that includes the patches (see Remediation).

#### Check Whether the Patched Image Is Deployed

The fix introduces the module `keystone.api._shared.delegation`, which only exists in patched
images:

```bash
docker exec keystone /var/lib/kolla/venv/bin/python3 -c "import keystone.api._shared.delegation" \
  2>/dev/null && echo patched || echo vulnerable
```

`vulnerable` means the running image does not contain the fix.

## Vulnerability Details

Keystone distinguishes *primary* authentication methods, which authenticate a user directly
(`password`, `token`, `totp`, `mapped`, `saml2`, `openid`, `external`, `kerberos`, `x509`), from
*delegated* credentials, which are deliberately narrow grants derived from a user
(`application_credential`, `ec2credential`, `oauth1`, and trust-scoped tokens). API endpoints that
mint a new, independent grant must reject delegated tokens, otherwise a narrow grant can bootstrap a
broader or longer-lived one. Before the fix these guards were implemented separately per endpoint,
and each of them recognized only some of the delegated methods.

### Bug #2153453 — Delegated tokens can create persistent delegations

- `_check_application_credential()` in `keystone/api/trusts.py` only blocked tokens whose methods
  included `application_credential`. Tokens derived from an OAuth1 access token or an EC2 credential
  could create, list, read, and delete trusts. Since trust creation validates the requested roles
  against the trustor's full role assignments rather than against the roles of the requesting
  token, such a token could also delegate roles the delegation was never scoped to.
- `_block_delegated_token_app_creds()` in `keystone/api/users.py` only checked for a `trust_id` or
  an OAuth1 `access_token_id` on the token, so an EC2-derived token — which carries neither — could
  create and manage application credentials and access rules.
- `PUT /v3/OS-OAUTH1/authorize/{request_token_id}` in `keystone/api/os_oauth1.py` only rejected
  trust-scoped, OAuth1-scoped, and application credential tokens, so an EC2-derived token could
  authorize OAuth1 request tokens and thereby mint new OAuth1 access tokens.

All three grants outlive the credential used to create them: revoking a leaked EC2 key pair or
OAuth1 access token does not remove the trusts, application credentials, or access tokens it
bootstrapped.

The fix introduces `keystone/api/_shared/delegation.py` with a deny-by-default allowlist of primary
authentication methods. `is_delegated_method()` treats every token whose methods are not entirely
primary — including an empty method list, which occurs for `ec2credential` tokens after a fernet
round-trip — as delegated, and all three endpoints now use this shared check. Application credential
tokens keep their documented behavior (the opt-in `[security_compliance]
allow_insecure_application_credential_trust_escalation` for trust management and the
unrestricted/restricted distinction for creating further application credentials); OAuth1 and EC2
credentials are blocked unconditionally.

### Bug #2158538 — Delegated tokens escape their project scope via token reauthentication

`token_authenticate()` in `keystone/auth/plugins/token.py` implements the token authentication
method, i.e. exchanging an existing token for a new one. Trust-scoped and OAuth1-scoped tokens were
rejected unconditionally, but application credential tokens were only rejected when an explicit
scope was requested: with the scope omitted, the request fell through to Keystone's default-project
scoping and returned a token for the credential owner's default project — a different project than
the one the application credential was bound to. EC2-derived tokens matched none of the checks and,
with the default `[token] allow_rescope_scoped_token = True`, could be rescoped to any project the
underlying user has a role in.

The fix rejects every delegated token from the token authentication method using the same shared
classification and returns HTTP 403.

### Prerequisite Changes

The upstream fix consists of two changes that are interdependent and must be applied together; OSISM
ships both in the patched images:

1. **trusts, oauth1, app-creds: reject delegated tokens across all endpoints**
   ([Bug #2153453](https://bugs.launchpad.net/keystone/+bug/2153453)) — introduces the shared
   delegation classification and the new `[auth] additional_primary_auth_methods` option and applies
   the check to trusts, application credentials, and OAuth1 authorization.
2. **auth: reject delegated tokens from token-method reauthentication**
   ([Bug #2158538](https://bugs.launchpad.net/keystone/+bug/2158538)) — applies the classification
   to the token authentication method and depends on the first change.

:::warning

Behavior changes after the fix:

- Any authentication method that is not built into Keystone is treated as a delegated credential and
  rejected from managing trusts, application credentials, and OAuth1 access tokens, and from token
  reauthentication. Deployments running a custom or third-party authentication plugin must list its
  method name in `[auth] additional_primary_auth_methods`, otherwise these workflows fail for users
  authenticated through it.
- Exchanging an application credential token or an EC2-derived token for a new token via the token
  authentication method is rejected with HTTP 403. Clients must authenticate with the application
  credential directly instead.

:::

### Additional Hardening in the OSISM Images

Besides the two upstream patches, the patched OSISM images for 2025.1, 2025.2, and 2026.1 contain
the upstream change *Ban ec2credential tokens from Keystone API*, which is merged on master but not
backported to the stable branches upstream. It rejects tokens derived from EC2 credentials for every
Keystone API call except token validation and re-authentication, closing the whole class of EC2
token issues at the API boundary. The behavior is controlled by the new option `[auth]
ban_ec2credential_tokens` (default `True`). Deployments that use EC2-derived tokens directly against
the Keystone API must set it to `False`.

## Remediation

### For OSISM Releases

Because no fixed Keystone release is available upstream, OSISM provides the fix as downstream
patches for the Keystone container images via the following change:

- [container-images-kolla commit 01ae42c](https://github.com/osism/container-images-kolla/commit/01ae42cdce2dc6c86927116fcce10c90a930122b)
  ([PR #776](https://github.com/osism/container-images-kolla/pull/776))

This change adds the patches for 2025.1 (Epoxy), 2025.2 (Flamingo), and 2026.1 (Gazpacho). The
community-curated backports for 2024.1 (Caracal) and 2024.2 (Dalmatian) are in preparation and will
be announced in an update of this advisory.

A fix will be included in upcoming OSISM releases that ship the patched Keystone container images.
Consult the [OSISM Release Notes](../../release-notes/) for version information and availability.

The affected code runs in the Keystone API service (`keystone` container). Using rolling tags,
override the Keystone container images in `environments/kolla/images.yml`. With a stable OSISM
release the Kolla images are pulled from the `kolla/release/<openstack_version>` namespace with
pinned version tags (`docker_namespace` in `environments/kolla/configuration.yml`), whereas the
rolling images live in the `kolla` namespace. The image parameters therefore have to be overridden
together with the tag; the tag override alone would point at an image that does not exist:

```yaml title="environments/kolla/images.yml"
keystone_tag: "2025.1"  # or "2025.2", depending on your OpenStack release
keystone_image: "registry.osism.tech/kolla/keystone"
keystone_fernet_image: "registry.osism.tech/kolla/keystone-fernet"
keystone_ssh_image: "registry.osism.tech/kolla/keystone-ssh"
```

Replace `registry.osism.tech` if you pull the images from a mirror. From 2025.2 on the Keystone
role additionally runs an `httpd` container (`keystone_httpd_image`, `keystone_httpd_tag`) that
contains no Keystone code; its tag follows `keystone_tag` by default, so pin `keystone_httpd_tag`
to the currently deployed tag when overriding `keystone_tag`.

### Mitigation

Because all deployments are affected and the vulnerabilities require only a delegated credential,
applying the patched container image is the only complete remediation. Until the fix is deployed —
in particular on 2024.1 and 2024.2 — consider the following measures:

1. Disabling the rescoping of scoped tokens closes the token reauthentication path (Bug #2158538).
   Add the following to the configuration repository and redeploy Keystone:

   ```ini title="environments/kolla/files/overlays/keystone.conf"
   [token]
   allow_rescope_scoped_token = False
   ```

   This also prevents legitimate clients from exchanging a scoped token for another scoped token;
   authenticating with an unscoped token or with credentials directly is not affected. It does not
   mitigate Bug #2153453.
2. Auditing existing delegations. Trusts, application credentials, EC2 credentials, and OAuth1
   access tokens that were created through a delegated token before the fix remain valid after it is
   applied and have to be revoked manually:

   ```bash
   openstack --os-cloud admin trust list
   openstack --os-cloud admin credential list --type ec2
   openstack --os-cloud admin consumer list
   openstack --os-cloud admin application credential list --user <user>
   ```

   Application credentials can only be listed per user. Trusts whose trustee is not a service user,
   and credentials or consumers nobody can account for, are candidates for removal.
3. Rotating EC2 credentials and OAuth1 access tokens that may have leaked. Rotating them is not
   enough on its own: trusts, application credentials, and OAuth1 access tokens that were created
   with such a credential before the rotation stay valid and have to be removed as described in
   point 2.
4. Monitoring the Keystone API logs for `POST /v3/OS-TRUST/trusts`,
   `POST /v3/users/{user_id}/application_credentials`, and `PUT /v3/OS-OAUTH1/authorize` requests
   from unexpected sources.
